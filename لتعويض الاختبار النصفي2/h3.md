# تمرين تطبيقي: تحليل الهجمات والحماية المتقدمة

## 1. هجمات حقن الكائنات (Object Injection)

تعتبر دالة `unserialize()` في PHP من الدوال الخطرة إذا تم استخدامها مع مدخلات المستخدم مباشرة.

### مثال على كود مصاب (Vulnerable Code):

```php
// استلام بيانات من المستخدم واستخدامها مباشرة في unserialize
$data = $_POST['data'];
$obj = unserialize($data); [cite_start]// ثغرة أمنية [cite: 909, 911]

```

### السيناريو الهجومي:

عند استدعاء `unserialize` على كائن محقون، يتم تفعيل "الدوال السحرية" (Magic Methods) مثل `__wakeup()` أو `__destruct()` تلقائياً.

**كائن هجومي لتنفيذ أوامر النظام:**

```php
class Vulnerable {
    private $command;
    public function __wakeup() {
        system($this->command); [cite_start]// تنفيذ أوامر النظام مباشرة [cite: 910]
    }
}

// السلسلة النصية المحقونة لتنفيذ أمر 'whoami'

```

## 2. المقارنة الأمنية بين Serialize و JSON

| المعيار | `serialize()` | `json_encode()` |
| --- | --- | --- |
| **تنفيذ الكود** | نعم، يستدعي `__destruct` و `__wakeup` 

 | لا، يعامل البيانات كنص فقط 

 |
| **إنشاء الكائنات** | ينشئ كائنات من الفئات المعرفة 

 | ينشئ مصفوفات أو كائنات بيانات بسيطة 

 |
| **الأمان** | خطير جداً مع مدخلات المستخدم 

 | آمن نسبياً وصعب التلاعب به تنفيذياً 

 |
| **الحجم والأداء** | أسرع قليلاً لكن الحجم أكبر 

 | أصغر حجماً وأكثر توافقاً مع اللغات الأخرى 

 |

### أ) استخدام القائمة البيضاء (Allowlist)

## 4. أفضل الممارسات الأمنية (الملخص)

1. 
**تجنب** `unserialize` تماماً مع أي بيانات قادمة من المستخدم واستبدلها بـ `json_decode`.


2. إذا كان لا بد من استخدامه، لا تقبل إلا فئات محددة مسبقاً (Allowlist).


3. استخدم التوقيع الرقمي للتأكد من مصدر وسلامة البيانات (Integrity Check).


4. قم بتعطيل الوظائف الخطرة في PHP التي قد تُستغل عبر هذه الثغرات مثل `system` أو `exec` إذا لم تكن ضرورية.
